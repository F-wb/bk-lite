## 1. 结论摘要

1. **不在平台内自研集群控制台，也不引入 KubeSphere 等重型平台。** 集群可视化与应急操作由外挂面板承担，平台只做"纳管、入口、联动、受控作业"。
2. **集成方式选定：平台 Provider 扩展包 + 深链新标签页跳转。** 这是上游官方设计的扩展点（`providers/builtin/` 自动扫描、Manifest 驱动表单），已有 JumpServer SSH 终端作为同类先例，**后端可做到零修改既有文件**。
3. **权限真正落到人，靠"一份集群导入两次"**：同一集群分别以只读凭证和可写凭证导入面板，运维组账号绑可写实例、研发组账号绑只读实例（设计动机见 9.1，为何不能靠面板自身角色见 9.6）。
4. **变更红线：面板不做发布。** 改镜像版本、编辑 YAML 一律禁止用于生产；生产发布只走 GitLab 打 tag 触发流水线 + `values-<环境>-<集群>.yaml` + 服务器端快照归档。面板只用于"看 + 应急动作"。
5. **110 老集群（v1.22.2）已纳管，但属“越过官方支持区间”的知情决定（2026-11-06 推翻本条原结论）。** 面板官方最低支持 Kubernetes v1.24，v1.23 及更早不在支持范围；但实况是 110 已导入面板且 `status.phase=Completed`（面板探测到 v1.22.2）。经决定：**保留纳管并把风险记一档**，不再宣称“不纳入”。详见 8.2 与 R3；事实出处 `ops/kubepi/panel-assets.yaml`。
6. 落地工作量：**P1 合计约 5 人天**，其中平台侧代码约 400 行 Python + 1 个前端组件（属新增功能开发，需确认由谁承接，见第 12 节角色提示）。
7. **落地进度（2026-11-05）**：面板已在生产 ops 机 `10.10.2.95` 上线——`/opt/kubepi` + 命名卷 `kubepi-data`（`external: true`），入口 `http://10.10.2.95:18080/kubepi`，非 privileged 运行，常驻 55MiB；91 试用实例已删除；迁移经 md5 全等校验，备份任务已建立并做过**还原验证**（8.4）；前置反代层评估后**已拆除**（6.1）。
8. **接域控只能统一认证，不能统一授权**：面板 LDAP 同步的用户角色写死为 `Common User`，详见 9.6。

## 2. 目标与非目标

### 2.1 目标

- 运维组、研发组在一个图形界面里完成**看集群、看负载、看日志、进容器排障、临时重启/扩缩**四类日常动作，不再依赖记忆 kubectl 命令和 SSH 到 master。
- 平台侧新增能力**不破坏跟进上游迭代的能力**：改动以"纯新增文件"为主，可随上游 merge 无损保留。
- 权限与审计可解释：谁能对哪个集群的哪个命名空间做什么，出事能追到人。
- 与既有资产职责清晰：监控/CMDB/日志/告警继续在平台，集群图形化操作在面板，常规变更在流水线。

### 2.2 非目标（明确不做）

| 不做 | 原因 |
|---|---|
| 在平台内做集群资源 CRUD 页面 | 重复造面板已有的能力，且需长期跟上游前端结构博弈 |
| 把面板当第二条发布通道 | 会与 `values-*` 规范、快照归档区产生"集群与 git 不一致"的永久漂移 |
| 集群生命周期管理（建集群/升级/证书轮换） | 面板不提供，属独立专项 |
| ~~纳管 110（v1.22.2）~~ **已推翻（2026-11-06）** | 原理由为“超出面板官方支持版本区间”；实际 110 已导入且面板连接成功，因此不再属于“不做”，而是“带风险在做”——风险记录见 8.2 与 R3 |
| 用面板替代平台已有的 CMDB 台账/监控/告警 | 双链路纳管机制保持不变，不重复采集 |
| 无人值守自动自愈 | 本期只做"人点按钮"；自愈闭环留待 P2 另立项 |

## 5. 架构总览

### 5.1 解耦四原则

1. **控制面与数据面分离**：面板是集群的一个普通 RBAC 客户端；平台不直连 apiserver，不持有集群凭据（凭据只在面板与流水线里）。
2. **单向依赖**：平台 → 面板（深链、健康自检）；面板 ⇏ 平台。面板挂掉不影响平台任何功能，反之亦然。
3. **纯新增、可摘除**：平台侧改动全部落在新增文件与数据配置；卸载面板后，平台只是少一个菜单，无残留故障。
4. **一个动作只有一个入口**：发布/回滚/配置变更 = 流水线；观察/排障/应急 = 面板；台账/指标/告警 = 平台。

### 5.2 组件与链路

```
                  ┌──────────────────────── 盛大运维系统（平台，compose）────────────────────┐
   运维/研发 ────▶│ Web 门户：CMDB 台账 · 监控中心 · 告警中心 · 集成中心(新增 kubepi 实例) │
                  └───────┬───────────────────────────────────────────────┬────────────────┘
                          │ ①只读采集（现状不变）                          │ ②深链跳转 execute_capability
              webhookd /infra/render                         平台 Provider: kubepi（新增包）
              ├─ metric 采集器 → VictoriaMetrics                      │ HTTP（面板 API 健康自检）
              └─ resource 采集器 → prometheus_kube_* → CMDB 台账      ▼
                  ┌────────────────── KubePi 面板（独立 compose/集群内 Deployment）────────┐
   运维/研发 ────▶│ 多集群导入 · 工作负载操作 · 日志 · Web 终端 · 按 cluster/ns 分权 · 审计 │
                  └───────┬───────────────────────────────────────────────────────────────┘
                          │ ③ Kubernetes API（各集群独立 ServiceAccount，最小权限）
                          ▼
              121 测试集群（读写/受限）    zz / yc / 141 生产集群（仅只读）    110（不纳管）
```

| 链路 | 内容 | 本期动作 |
|---|---|---|
| ① 纳管只读 | 双链路采集、台账、指标、日志、告警 | **保持现状不动**，不新增采集器 |
| ② 入口联动 | 平台集成中心管面板实例与凭据；CMDB/告警一键跳转 | **本期新增**（P0 配置级，P1 代码级） |
| ③ 图形化操作 | 面板 RBAC 客户端操作集群 | **本期新增**（外部服务，不进平台代码） |

## 6. 耦合形态选型与否决理由

| 方案 | 形态 | 耦合度 | 跟进上游影响 | 结论 |
|---|---|---|---|---|
| A | 零配置：仅浏览器书签 + 文档 | 无 | 无 | ✅ **P0 采用**（当天可用，作为 P1 的兜底） |
| B | 集成中心录外部实例 + **Provider 扩展包**做健康自检与深链（复用 F5 契约） | 低（HTTP） | 纯新增目录 + 前端 1 处挂载 | ✅ **P1 选定** |
| C | iframe 内嵌面板页面 | 中 | 需改平台前端布局 | ❌ 否决：F6 实测跨站 Cookie 在 iframe 内不发送，会话类页面直接故障；且双前端样式/路由耦合 |
| D | 平台自研集群管理模块（新 app + 新页面 + K8s client） | 高 | 每次上游 merge 都要抢救前后端结构、权限项、语言包、表迁移；上游有"模块改名连表名一起改"的先例 | ❌ 否决：重复实现 F7 面板已有能力，长期维护成本刚性，且超出使用者角色职责边界 |
| E | 引入 KubeSphere 全家桶 | 高 | 其 DevOps/监控/告警与流水线、平台监控中心、告警中心三方重叠，产生两套真相 | ❌ 否决：目标只是"应急时有个网页能点"，投入产出不成比例 |
| F | 面板写操作走 OpsPilot AI 工具 | 低 | 上游模块 | ❌ 本期不采用：F2 显示破坏性操作无审批门、参数由模型生成；先做确定性图形界面，AI 只做只读诊断与命令建议 |
| G | 面板前置反向代理（独立 traefik 容器做 TLS + 访问日志） | 低 | 无 | ⚠️ **已实施后拆除**，见 6.1 |

### 6.1 反代层的评估结论（2026-11-05 实测后拆除）

当初列的三条收益，逐条拿证据复核后只剩一条成立：

| 声称的收益 | 实测结果 | 成立 |
|---|---|---|
| 「地址变更只改反代，绕开死快照」 | 应用 `is_build_in=True` 时 `current_user_apps` 会回 App 表刷新最新 url（F14）→ 改应用表一条记录即全量生效，反代在此**无贡献** | ❌ |
| 「跳转有服务端留痕，补审计」 | 反代在认证之前，access log 里 `ClientUsername` 恒为 `"-"`，**只记到真实 IP（实测 `10.10.40.81`）记不到是谁**；「谁做了什么」面板自身有登录与操作审计 | ⚠️ 被夸大 |
| 「HTTPS，凭据不明文过网」 | 唯一真实收益；但用的是自签证书，防被动嗅探不防 MITM | ✅ |

成本则实测明确：多 1 个容器（19MiB）、多 2 份配置（`traefik.yml`/`dynamic.yml`）、多 1 个故障点、外加一份无轮转的日志。**用这些只换一条「加密」不划算，故拆除**，回到单容器直连 18080。

**何时应重新加上反代**：需要 `auth_request` 前置鉴权、来源 IP 白名单、或对入口做统一限速/审计聚合时——反代是唯一能插桩的位置。若只是想要加密，优先用面板自带的 `app.yml` → `ssl.enable/certificate/certificateKey`（F15 同仓库配置），不必加容器；但该配置的实际端口语义尚未实测（Q9）。

### 7.2 改动清单与 merge 风险评估

| 路径 | 类型 | 规模 | 上游冲突风险 |
|---|---|---|---|
| `providers/builtin/kubepi/**` | **新增目录** | ~300 行 | 无（上游不会在这些路径产生文件；加载器自动发现，无需注册代码） |

### 7.4 能力与操作

| capability | operation | 输入 | 返回 `payload` |
|---|---|---|---|
| （base_connection） | `test_connection` | 实例配置 | 无；失败用 `provider.invalid_config` / `provider.auth_failed` / `provider.timeout` |
| `cluster_console` | `build_console_url` | `cluster_uid`, `namespace`, 可选 `resource_kind`/`resource_name`, `platform_user` | `console_url`, `cluster_uid`, `mode`, `expire_seconds` |
| `cluster_console` | `list_console_clusters` | 无 | `clusters[]`（含 `uid/name/k8s_version/supports_console`） |

响应统一 `CapabilityExecutionResult.success_result/failed_result`，禁止直接返回面板原始响应体（上游 §12）。深链一律**新标签页顶层打开**（依据 F6）。

### 7.5 客户端与日志红线（沿用上游 §8）

- 超时：连接 3s / 读 10s，非幂等不重试；超时返回 `provider.timeout` 且 `retryable=True`。
- **禁止**在日志输出令牌、完整 URL（含 query）、面板响应正文、无界对象；只打结构化事件名 + 标识符。
- 数据访问只用 Django ORM；本 Provider 设计不写平台业务表（无迁移、无新表），因此**不引入数据库结构变更**——这是"不影响跟进上游"的关键保障。

| 卸载 | 删除 compose 项目 + 卷 + 集成实例/应用记录；平台无残留 |

## 9. 安全设计（RBAC）

### 9.1 每集群两套 ServiceAccount 原则

**一个集群导入两次**：`kubepi-readonly` 与 `kubepi-ops`。原因（重要）：面板账号体系与 Kubernetes 身份默认不打通，若只导一份可写凭据，则"面板用户权限"与"集群实际权限"是两套账，任何能登录面板的人都共享同一集群身份。用两份凭据 + 面板侧用户-集群绑定，才能让权限真的分到人。

> 若后续核实面板支持 impersonation 或 LDAP/CAS 对接（Q4/Q8），可收敛为单份凭据 + 按人鉴权。

### 9.2 权限矩阵（逐集群）

| 资源 | `kubepi-readonly`（研发 & 生产） | `kubepi-ops`（运维，仅测试集群） |
|---|---|---|
| pods / pods/log / pods/status | get, list, watch | get, list, watch, **delete**, **evict** |
| pods/exec | ❌（研发组如需，单独立项审批后按 ns 放开） | ✅ 仅测试集群 |
| deployments / statefulsets / daemonsets / replicasets | get, list, watch | + get, list, watch, **patch**, **scale 子资源** |
| services / ingress / events / configmaps | get, list, watch | get, list, watch（**不含写**） |
| secrets | ❌ **完全禁止**（读写都禁） | ❌ 禁止 |
| nodes / persistentvolumes / claims | get, list, watch | get, list, watch |
| namespaces / RBAC / CRD | get, list, watch | ❌ 写权限禁止 |
| 任意 `*/*` 或 cluster-admin | ❌ | ❌ |

**明确不给**：`pods/deletecollection`、`deployments/delete`（生产删负载必须走流水线）、`secrets` 任何动词、`nodes` 写（无 cordon/drain 需求）。

### 9.3 凭据签发注意（版本相关）

v1.24+ 起 ServiceAccount 不再自动创建 token Secret，需要**显式创建 `kubernetes.io/service-account-token` 类型 Secret** 来签发长效令牌；或以面板"导入 kubeconfig"方式粘贴。落地时按面板实际支持的导入方式（Q3）选择，并在文档附录给出对应命令模板。

### 9.4 平台侧安全边界

- 平台**不持有 kubeconfig、不直连 apiserver**；集成实例只存面板地址与令牌，令牌由平台加密存储（F3 必测行为：secret 字段保存后加密、回显脱敏）。
- 跳转不携带集群凭据，只携带定位参数；深链目标 URL 由服务端白名单模板拼装，禁止拼接用户输入的自由路径（防 SSRF/开放重定向）。

### 9.5 审计

| 层 | 记录内容 | 缺口 |
|---|---|---|
| 平台 | 谁、何时、从哪个 CMDB 实例/告警点开了哪个集群的哪种视图（`execute_capability` 调用日志） | 只记录"打开"，不记录面板内做了什么 |
| 面板 | 登录、工作负载操作、exec、YAML 变更 | 与平台日志的用户名/时间戳需人工对齐 |

**改进项（P1 内）**：深链生成时写入结构化审计事件，字段固定为 `event=kubepi_console_granted provider_key= kubepi user= cluster_uid= namespace= mode= request_id=`；面板用户与平台用户名**强制同名**（拼音工号），使两侧日志可 join。

### 9.6 统一身份（域控）能解决什么、不能解决什么

依据 F15（面板 LDAP 源码实测结论）：

| 诉求 | 接域控后能否达成 | 说明 |
|---|---|---|
| 一套账号口令、免二次登录 | ✅ 能 | 面板原生 LDAP：BaseDN / Filter / SizeLimit / TLS / 字段 Mapping，登录走 LDAP bind 校验 |
| 角色自动对齐（平台 guest ↔ 面板角色） | ❌ 不能 | 同步进来的用户被**硬编码**为 `Common User`（源码两处），无任何「AD 组 → 面板角色」映射配置项 |
| 账号生命周期自动收敛 | ❌ 不能 | 同步**只增不删不改**：AD 里离职/改名/改邮箱，面板侧账号与权限不会跟着变 |
| 多目录/多域 | ❌ 不支持 | 只取第一条 LDAP 配置（`ldaps[0]`） |

**所以分权只有三条路：**

| 路径 | 做法 | 评价 |
|---|---|---|
| **A（推荐）** | 不依赖面板角色，靠**两套集群凭据**（只读库给研发、可写库给运维）+ 面板用户↔实例绑定 | 权限上限由 K8s RBAC 兜住，面板自身角色只当「可见性」用；即 9.1 原设计 |
| B | LDAP 认证 + 自写**幂等同步脚本**按 AD 组补 `RoleBind` | 可行，但脚本要自己负责「删与改」（LDAP 同步不做），额外维护成本 |
| C | 只接 LDAP，接受所有人都是 `Common User` | 等于放弃分权，仅适合纯只读场景 |

**结论：走 A + 接 LDAP 管认证。** 「平台导入是 guest、面板是 Common User」是两个体系各自的默认值撞巧，不是一条授权链路，不可当作已分权。

## 10. 变更红线与发布边界

1. **生产集群（zz/yc/141）面板一律只读。** 任何生产写操作在 RBAC 层就不存在，不依赖人的自觉。
2. **面板上改了就必须在 24 小时内回灌 git。** 测试集群若用了面板的"换镜像版本/编辑 YAML"，必须在服务器端快照归档区（`/home/shengda/charts/<集群>/<服务>/<日期>-<chart版本>/`）补一条说明，并把差异合回 `values-<环境>-<集群>.yaml`。归档区规则第 2 条要求 `deployed-*` 文件是"集群真实状态的证据"，面板改动会让它与 git 分叉，必须显式记录。

## 附录 C：RBAC 模板要点

- `kubepi-readonly`：ClusterRole 仅 `get/list/watch`，覆盖 pods、pods/log、deployments、statefulsets、daemonsets、services、ingresses、events、configmaps、nodes、persistentvolumes、persistentvolumeclaims；**不含 secrets、不含 pods/exec**。
- `kubepi-ops`（仅测试集群）：在 readonly 基础上追加 `pods: delete`、`pods/eviction: create`、`deployments+statefulsets: patch`、`deployments/scale+statefulsets/scale: patch`、`pods/exec: create`。
- 两者均通过 `RoleBinding` 收敛到授权命名空间；`kubepi-ops` 的 ClusterRoleBinding 只在测试集群存在。
- 令牌签发遵循 9.3（v1.24+ 需显式 token Secret）。
