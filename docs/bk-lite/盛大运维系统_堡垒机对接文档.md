# 盛大运维系统 · 堡垒机（JumpServer）对接文档

> **文档用途**：说明盛大运维系统与堡垒机（JumpServer）的对接方式、认证原理、部署前提与注意事项，供部署、联调、排错与交接使用。
>
> **适用版本**：盛大运维系统 v1.0（对接 JumpServer v5.0.0-ce 实测通过）
> **最后更新**：2026-10-15

## 零、对接前必读（给对接人）

> 本节是接入前必须先确认的事项。绝大多数「连不上」「403」「查得到但连不上」都源于下面的映射没对齐。

### 0.1 身份映射键就是「用户名」`username`

堡垒机**不认**平台的账号 ID，只认**用户名**。整条链路有三处映射，全部围绕它：

| 环节 | 匹配键 | 规则 |
|---|---|---|
| 平台用户 → 堡垒机用户 | **`username`** | 平台登录名 = 堡垒机用户名，**精确匹配、区分大小写**；不存在时按**同名**自动创建（受 `auto_create_user` 控制） |
| 资产定位 | **IP** | 先用 `address` 精确匹配，未命中再用 `name` 精确兜底（兼容「堡垒机资产以主机 IP 命名、实际连接地址为网关映射地址」） |
| 资产上的系统账号 | **`username == default_system_user`** | 建令牌时传的是该账号的 **UUID（id）**，**不是账号名** |

> `email` / `display_name` 只在创建堡垒机用户时带上，**不参与匹配**。

### 0.2 接入前必须确认的四件事

1. **用户名对齐**：平台每个要连堡垒机的账号，在堡垒机里**有同名用户**（或允许自动创建）；用户名不一致会直接失败。
2. **堡垒机侧授权**：该用户在该资产上被授权，且必须**同时覆盖「该资产 × `ssh` 协议 × 对应系统账号」**——缺任一维都会被拦在建令牌阶段（400 `perm_account_invalid`）。
3. **平台侧准入**：平台账号需具备 cmdb 的 **`asset_info-View`** 权限（否则接口 403，请求根本到不了堡垒机）。仅超管账号可绕过该检查，故**验收必须用非超管账号**。
4. **系统账号存在**：`default_system_user`（默认 `root`）在该资产的系统账号列表中**必须存在**；未命中会直接失败（`provider.system_user_not_found`，2026-10-15 起不再回退到其他账号）。

> 一句话：**用户名对齐 + 堡垒机侧资产授权 + 平台侧 `asset_info-View` + 系统账号存在**，四者缺一不可。

### 0.3 两条通道与最终闸门

| | ① 服务端通道 | ② 浏览器通道 |
|---|---|---|
| 认证 | 平台持有的 Admin API `api_key/api_secret` + HMAC 签名 | 用户自己的堡垒机登录会话 Cookie + 一次性令牌 |
| 能否决定「谁能连」 | **不能**（管理员视角，可查全部资产） | **能**（按用户本人做资产授权校验） |

**最终闸门在堡垒机侧的「建令牌」这一步**，按用户本人判定；平台凭证再高权限也过不了它。因此「查得到 ≠ 连得上」，排错时不要用「资产查询成功」当作有权限的证据。详细原理见第三章。

### 0.4 常见坑速查

| 现象 | 根因 | 处理 |
|---|---|---|
| 接口 403 | 平台账号无 cmdb `asset_info-View` | 给账号授权（注意是 **cmdb** 应用，非 system-manager） |
| 400 `perm_account_invalid` | 堡垒机侧该用户在此资产/账号/协议上无授权 | 在堡垒机补资产授权 |
| 提示系统账号未找到 | `default_system_user` 在该资产上不存在 | 改配置或用资产上实际存在的系统账号 |
| 用户名不匹配 | 平台与堡垒机用户名不一致（大小写敏感） | 统一用户名或开启自动创建 |
| 打开终端报「无法连接 Koko」 | 跨站 iframe 导致会话 Cookie（SameSite=Lax）不发送 | 已改为新标签页打开，勿再改回 iframe |

## 一、能力概述

### 1.1 业务场景

在 **CMDB 资产详情页**点击「SSH 终端」按钮，以**新标签页**打开堡垒机 Web 终端（Luna / Koko），直接对该资产发起 SSH 会话，无需切换到堡垒机再找资产。

### 1.2 集成的能力

Provider `jumpserver` 下提供两个能力：

| 能力 key | 名称 | 说明 |
|---|---|---|
| `ssh_terminal` | SSH 终端 | 创建连接令牌并返回 Luna 终端 URL |
| `asset_query` | 资产查询 | 按 IP 查询堡垒机资产信息 |

### 1.3 一次点击的完整链路

```
用户点击「SSH 终端」
  → 前端先同步打开空白标签页（避免异步返回后被浏览器拦截）
  → POST /api/v1/system_mgmt/integration_instance/execute_capability/
       provider_key=jumpserver, capability_key=ssh_terminal,
       operation=create_terminal_session, params={username, display_name, email, ip}
  → 后端（持有堡垒机 Admin API 凭证）：
       ① 按 IP 匹配堡垒机资产
       ② 查/建同名堡垒机用户
       ③ 匹配资产上的系统账号
       ④ 创建一次性连接令牌（account = 账号 UUID）
       ⑤ 拼装终端 URL 返回
  → 前端把标签页跳转到 terminal_url（堡垒机域名）
  → 浏览器携带堡垒机登录会话 Cookie 访问 Luna/Koko
  → 未登录则跳转堡垒机登录页，登录后回到终端
  → 终端建立
```

## 二、集成配置

### 2.1 配置项

在「系统管理 → 集成实例」中新建 `jumpserver` 实例，配置项如下（定义见 `server/apps/system_mgmt/providers/builtin/jumpserver/manifest.py`）：

| 配置项 | 界面标签 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|---|
| `base_url` | JumpServer 地址 | string | 是 | — | 堡垒机服务地址，**不含尾部斜杠** |
| `api_key` | API Key | password | 是 | — | 堡垒机 Admin API Access Key，建议配置为密文 |
| `api_secret` | API Secret | password | 是 | — | 堡垒机 Admin API Secret，建议配置为密文 |
| `verify_ssl` | 校验 SSL 证书 | boolean | 否 | `true` | 自签名证书导致连接失败时关闭 |
| `default_system_user` | 默认系统账号 | string | 否 | `root` | SSH 登录默认使用的**系统账号用户名** |
| `token_expire_seconds` | Token 过期时间（秒） | number | 否 | `3600` | ⚠️ 实际不生效，见 3.5 |
| `auto_create_user` | 自动创建用户 | boolean | 否 | `true` | 用户首次连接时自动在堡垒机创建同名账号 |

### 2.2 凭证获取

堡垒机侧在「系统设置 → API Key」中创建 Access Key / Secret Key，填入 `api_key` / `api_secret`。该凭证为**管理员级**，对应堡垒机的 Admin API。

### 2.3 实例生效条件

后端按 `provider_key='jumpserver'` 且 `enabled=true`、`status=ready` 查询实例并取第一条。**若没有 ready 实例，接口直接返回 404**：

```
{"success": false, "summary": "No ready integration instance for provider 'jumpserver'"}
```

## 三、认证原理

### 3.1 两层认证（彼此独立，不可互相替代）

| | ① 服务端通道 | ② 浏览器通道 |
|---|---|---|
| 两端 | 平台后端 ↔ 堡垒机 Core API | 浏览器 ↔ Luna / Koko |
| 认证方式 | Admin API `api_key/api_secret` + HMAC-SHA256 `Signature` 签名 | 堡垒机**登录会话 Cookie**（`jms_sessionid`）+ 一次性连接令牌 |
| 代表身份 | **平台自己**（相当于堡垒机的 API 客户端/管理员） | **用户本人** |
| 作用 | 准备令牌与终端 URL（可查全部资产、建用户、建令牌） | 真正建立终端连接 |

> 关键：服务端通道只是把「令牌 + 终端 URL」准备好；**真正拉起终端的是浏览器自己的登录会话**。所以平台侧凭证再高权限，也不能替代用户登录堡垒机。

签名头的构造逻辑见 `server/apps/system_mgmt/providers/builtin/jumpserver/adapters/client.py` 的 `_build_auth_headers`。

### 3.2 用户身份映射

平台用户名 → 堡垒机**同名用户**，按 `username` **精确匹配**（区分大小写）：

- 已存在 → 直接复用（`GET /api/v1/users/users/?username=`）；
- 不存在 → 用 Admin API 创建（`POST /api/v1/users/users/`，由堡垒机自动分配默认角色）；
- 可用 `auto_create_user=false` 关闭自动创建，此时找不到用户会直接失败。

> **因此用户名是两边的关联键**：平台用户张三，必须在堡垒机里也有用户名 `张三`。

### 3.3 权限闸门（核心）

创建连接令牌时，JumpServer 会拿请求体中的 `user` 做**该用户自己的资产授权校验**：

```
ConnectionToken.get_user_permed_account(user, asset, account_alias, protocol)
  → PermAssetDetailUtil(user, asset).validate_permission(account_alias, protocol)
      ├─ 校验收 ：该用户在本资产上被授予的协议是否包含 ssh
      └─ 校验账号：该用户在本资产上被授予的账号集合中是否存在该 alias
```

由此得出两条结论：

1. **普通用户只能连到他在堡垒机里被授权的资产**，且授权必须同时覆盖「该资产 × 对应账号 × `ssh` 协议」。
2. **平台的 API Key 权限再大也过不了这道闸门**——权限判定用的是"用户"，不是"调用方"。

⚠️ **资产查询走的是管理员 API**，所以平台能"查得到"用户实际无权访问的资产；真正被拦截发生在**建令牌**那一步。具体逻辑见 3.4。

### 3.4 资产查询阶段的权限校验逻辑

资产查询有两条路径：**SSH 终端流程内的第 ① 步（查资产）**，以及**独立的 `asset_query` 能力**。两者的权限行为完全一致。

#### ① 平台侧准入——这是唯一的一道校验

`execute_capability` 接口本身受平台权限控制（`server/apps/system_mgmt/viewset/integration_instance_viewset.py`）：

```python
@action(methods=["POST"], detail=False, url_path="execute_capability")
@HasPermission("asset_info-View", app_name="cmdb")
def execute_capability(self, request, *args, **kwargs):
```

即：**只有拥有 `asset_info-View` 权限的平台账号才能调用**。权限不足时接口直接返回 403，请求根本不会到达堡垒机。

> **应用归属必须显式指定（重要）**：`asset_info-View` 是 **cmdb** 应用的权限码，而 `HasPermission` 默认按被装饰方法所在模块推导应用名（本 ViewSet 位于 `system_mgmt` 模块 → 经映射为 `system-manager`），该应用的权限表中**并无** `asset_info-View`，两个应用的权限集合不交叉。若不显式传入 `app_name="cmdb"`，普通运维账号（非超管）调用会**必然 403**（仅超管因 `is_superuser` 旁路可通过）。此问题已于 2026-10-15 修复（提交 `00efe0b23`）。

#### ② 堡垒机侧——不按用户维度过滤

查询使用的是平台持有的 **Admin API 凭证**，属管理员视角，请求中**不携带平台用户身份**（`client.get_asset_by_ip`）：

```python
params = {"address": ip}                                  # ① 先按 address 精确查
response = self.get("/api/v1/assets/assets/", params=params)
# 未命中则改用 {"search": ip} 再查一次，并对结果做 address / name 的【精确】二次比对
```

| 检查项 | 是否执行 |
|---|---|
| 该平台用户是否有权访问此资产 | ❌ **不检查** |
| 该资产是否 `is_active` | ❌ 不过滤（仅作为字段返回） |
| 平台用户 → 堡垒机用户的对应关系 | ❌ 查询时不需要（`asset_query` 入参只有 `ip`，没有 `username`） |
| 平台账号是否具备 `asset_info-View` | ✅ 检查（见上方 ①） |

#### ③ 结论与边界

- **查询阶段不校验"用户是否有权访问该资产"**，所以平台能查到用户实际无权访问的资产；
- 真正的拦截**只在建令牌阶段**由堡垒机按"用户本人"执行（见 3.3），表现为 400 `perm_account_invalid`；
- 因此「**查得到 ≠ 连得上**」：排错时不要把"资产查询成功"当作"有权限"的证据。

#### ④ 调用示例（`asset_query`）

```
POST /api/v1/system_mgmt/integration_instance/execute_capability/
Authorization: Bearer <平台登录 token>

{ "provider_key": "jumpserver", "capability_key": "asset_query",
  "operation": "query_asset", "params": { "ip": "192.168.1.11" } }
```

成功时返回 `payload.asset`：

```json
{ "id": "…", "name": "192.168.1.11", "ip": "10.10.40.81",
  "platform": "Linux", "protocols": ["ssh"], "is_active": true, "comment": "" }
```

未命中资产时返回 `success: false` + `"Asset with IP or name … not found"`（**注意：这仍然只代表没查到资产，不代表用户无权限**）。

#### ⑤ 匹配细节（会影响结果）

- 先用 `address` 精确查 → 未命中再用 `search` 模糊查 → 但对模糊结果要求 `address == ip` **或** `name == ip` **精确相等**才采纳，因此不会把模糊命中的无关资产当结果；
- 若多条资产的 `name` / `address` 相同，**只取 API 返回顺序中的第一条**，不作歧义提示。资产命名重复时需人工确认匹配对象。

### 3.5 为什么必须用新标签页打开

堡垒机的会话 Cookie 名为 `jms_sessionid`，Django 默认 `SESSION_COOKIE_SAMESITE=Lax`。当终端页面被**跨站 iframe** 嵌入时，该 Cookie 属于第三方上下文、不会被发送，终端就会报「无法连接 Koko」。

因此在顶层导航（新标签页）中打开，Cookie 才能正常携带。前端实现见 `web/src/app/cmdb/components/SshTerminalButton.tsx`。

> 若确需保留 iframe，需在堡垒机侧放开 SameSite（`SESSION_COOKIE_SAMESITE=None`、`CSRF_COOKIE_SAMESITE=None`，且要求 `SESSION_COOKIE_SECURE=True`）。该改动位于堡垒机 core 容器镜像内、升级会丢失，并会降低 CSRF 防护，不建议采用。

### 3.6 连接令牌的生命周期

| 项 | 实际行为 |
|---|---|
| 有效期 | **5 分钟**（`CONNECTION_TOKEN_ONETIME_EXPIRATION` 默认 `5*60`，core 侧强制下限 300s） |
| 次数 | **一次性**，用过即废 |
| `token_expire_seconds` | ⚠️ **配置项不生效**。实测库中令牌 created→expired 恰好 300s，传 3600 也被忽略 |

**因此**：点击按钮后必须在 5 分钟内完成堡垒机登录/连接，超时需重新点击获取新令牌。

## 四、调用链与接口

### 4.1 前端入口

| 项 | 内容 |
|---|---|
| 组件 | `web/src/app/cmdb/components/SshTerminalButton.tsx` |
| 挂载点 | `web/src/app/cmdb/(pages)/assetData/detail/baseInfo/list.tsx` |
| 显示条件 | 实例存在 IP（`ip_addr` / `ip`）且非 IPAM 网段（`subnet`）模型；host 之外的资产模型（如虚拟机）同样显示 |
| 请求头 | **必须携带** `Authorization: Bearer ${token}`，否则后端鉴权中间件直接返回 401 |

### 4.2 平台接口

```
POST /api/v1/system_mgmt/integration_instance/execute_capability/
Authorization: Bearer <平台登录 token>
Content-Type: application/json

{
  "provider_key": "jumpserver",
  "capability_key": "ssh_terminal",
  "operation": "create_terminal_session",
  "params": { "username": "…", "display_name": "…", "email": "", "ip": "…" }
}
```

**响应信封（重要）**：平台统一返回 `{ result, code, message, data }`，业务数据在 `data` 内，需多剥一层：

```json
{
  "result": true, "code": "20000", "message": "success",
  "data": {
    "success": true,
    "summary": "SSH terminal session created",
    "payload": {
      "terminal_url": "https://<堡垒机域名>/luna/koko/connect/?token=<令牌id>&protocol=ssh",
      "token": "<令牌 id>",
      "asset_name": "192.168.1.11",
      "system_user": "root",
      "expire_seconds": 3600
    },
    "errors": []
  }
}
```

> 常见坑：只判 HTTP 状态码会漏判；后端成功但前端读 `data` 外层字段会得到 `undefined`。前端需同时判 `response.ok`、`body.result === false` 与 `data.success`。

### 4.3 后端内部步骤

`ssh_terminal.py → create_terminal_session`：

1. 校验 `username` / `ip` 必填；
2. **查资产**：先按 `address` 精确匹配 IP，未命中再按 `name` 精确兜底（兼容"堡垒机资产以主机 IP 命名、实际连接地址为网关映射地址"的场景，如 `name=192.168.1.11` / `address=10.10.40.81` / `port=2222`）；
3. **解析用户**：`get_or_create_user(username, display_name, email)`；
4. **匹配系统账号**：拉取资产系统账号列表，按 `username == default_system_user` 匹配；**未命中即失败**，返回 `provider.system_user_not_found`（detail 带 `available_accounts` 便于排错），**不再回退**其他账号（2026-10-15 起）；
5. **建令牌**：`account` 传**系统账号的 id（UUID）**，见 4.4；
6. **拼 URL**：`{base_url}/luna/koko/connect/?token=<令牌id>&protocol=ssh`。

### 4.4 `account` 字段必须传账号 UUID（关键）

`account` **不是账号名**。真实账号的 `alias` 就是它的 **id（UUID）**，只有虚拟账号才是 `@INPUT` / `@USER` 等。实测同一入参仅换 `account`：

| 传入 `account` | 结果 |
|---|---|
| 账号 UUID | **201 Created**（成功拿到令牌） |
| `root`（账号名） | **400** `perm_account_invalid` / 账号未找到 |
| `@INPUT` | **400** |

### 4.5 调用到的堡垒机 Admin API

| 用途 | 方法 | 路径 |
|---|---|---|
| 查用户 | GET | `/api/v1/users/users/?username=<name>` |
| 建用户 | POST | `/api/v1/users/users/` |
| 查资产 | GET | `/api/v1/assets/assets/?address=<ip>` 或 `?search=<ip>` |
| 查资产系统账号 | GET | `/api/v1/accounts/accounts/?asset=<asset_id>` |
| 建连接令牌 | POST | `/api/v1/authentication/connection-token/` |
| 终端页面 | GET | `/luna/koko/connect/?token=<令牌id>&protocol=ssh` |

建令牌请求体：

```json
{ "user": "<堡垒机用户 id>", "asset": "<资产 id>", "account": "<系统账号 id(UUID)>",
  "protocol": "ssh", "connect_method": "web_cli", "expire_seconds": 3600 }
```

## 五、部署前提（必须全部满足）

1. **堡垒机存在目标资产**：资产的 `address` 或 `name` 与 CMDB 主机 IP **精确相等**；
2. **资产上配置了可用的系统账号**（如 `root`），或授权中包含 `@INPUT` 等虚拟账号；
3. ⚠️ **该（同名）用户在堡垒机上有资产授权**，且授权覆盖「本资产 × 对应账号 × `ssh` 协议」——缺失则必然 400；
4. **浏览器已登录堡垒机**（会话 Cookie `jms_sessionid` 有效）；
5. **平台侧存在 `enabled + status=ready` 的 jumpserver 实例**。

**关于第 3 条（最常见的部署事故）**：
自动创建出来的堡垒机用户**默认没有任何授权**，因此新用户第一次点击必然 400，必须由**堡垒机管理员**把它（或其所属用户组）加入相应资产授权后才能真正使用。
本系统不会、也不应自动为用户授予权限。

## 六、注意事项与坑

| # | 项 | 现象 | 原因 | 处理 |
|---|---|---|---|---|
| 1 | 用户名不一致 | 平台用户点了没权限 | 平台按**同名精确匹配**找堡垒机用户；找不到会新建一个无授权的账号 | 保证两边用户名一致；或由堡垒机管理员给新用户补授权 |
| 2 | 无资产授权 | 400 `perm_account_invalid`（账号未找到） | 权限闸门按"用户本人"的资产授权校验（见 3.3） | 在堡垒机为该用户/用户组配置资产授权（含 `ssh` 协议与账号） |
| 3 | 报错文案误导 | 提示"账号未找到"，但账号明明存在 | 该错误码同时覆盖"资产/协议无授权"与"账号不在授权集合内" | 优先排查**资产授权**，而不是先怀疑账号不存在 |
| 4 | 跨站 iframe | 终端报「无法连接 Koko」 | `jms_sessionid` 为 `SameSite=Lax`，iframe 内不发送 | 以**新标签页**打开（已实现） |
| 5 | 令牌 5 分钟一次性 | 点开后慢一点就连不上 | core 强制下限 300s 且 `token_expire_seconds` 不生效 | 5 分钟内完成登录/连接，超时重新点击 |
| 6 | 资产命名 | 按 IP 查不到资产 | 堡垒机资产可能以 IP 命名、地址却是网关映射地址 | 已内置 `name` 精确兜底；也需保证 `name`/`address` 与主机 IP 精确相等 |
| 7 | 请求头缺失 | 401 未授权 | 后端鉴权中间件只从请求头取 token | 前端必须带 `Authorization: Bearer <token>` |
| 8 | 响应信封 | 后端成功前端报失败 | 业务数据在 `{result, code, message, data}` 的 `data` 内 | 前端需解包 `data` |
| 9 | SSL 自签名 | 连接校验/请求失败 | 堡垒机使用自签名证书 | 关闭 `verify_ssl` |
| 10 | 权限全局放开的风险 | 用户能连"所有"资产 | 授权若为「账号 `@ALL` + 协议 `all` + 节点 `DEFAULT`」即覆盖全部资产 | 按最小权限原则细分授权；此时需确保平台自动创建的同名用户已入授权 |

## 七、排错手册

### 7.1 后端日志抓手

在 server 容器日志中按以下 `event` 关键字定位：

| event | 含义 |
|---|---|
| `jumpserver_asset_found` | 资产匹配成功（含 `asset_id` / `asset_name` / `ip`） |
| `jumpserver_user_resolved` | 用户解析成功（含 `user_id` / `username`） |
| `jumpserver_system_user_not_found` | 默认系统账号在该资产上未命中，请求已失败（2026-10-15 起不再回退到其他账号） |
| `jumpserver_terminal_session_created` | 令牌创建并生成终端 URL 成功 |
| `jumpserver_terminal_session_failed` | 异常失败（`logger.exception`，含堆栈） |

### 7.2 排查顺序

```
1) 看 HTTP 状态
   404 → 无 ready 的 jumpserver 实例（检查实例 enabled/status）
   401 → 前端未携带 Authorization
   400 → 多为权限/字段问题，看后端返回的 code
2) 看后端日志 event 走到哪一步
   停在 asset → 资产匹配失败（address/name 与 IP 不精确相等）
   停在 user  → auto_create_user 关闭且用户不存在，或建用户失败
   停在 token → 权限闸门未通过（见 3.3 / 第五节第 3 条）
3) 核对第五节 5 条部署前提
4) 仍不通 → 按 7.3 取证
```

### 7.3 取证命令（堡垒机侧）

以下命令在堡垒机宿主机上以 jms_core 容器执行，用于确认授权与账号状态：

```bash
# 平台用户对应的堡垒机用户是否在目标资产的授权内
docker exec -i -w /opt/jumpserver/apps jms_core python3 manage.py shell <<'PYEOF'
from perms.utils import PermAssetDetailUtil
from users.models import User
from assets.models import Asset
u = User.objects.get(username="admin")          # 换成平台用户名
a = Asset.objects.get(name="192.168.1.11")      # 换成目标资产
util = PermAssetDetailUtil(u, a)
print("协议:", util.get_permed_protocols_for_user(only_name=True))
print("授权账号:", [(x.alias, x.username) for x in util.get_permed_accounts_for_user()])
print("校验 root/ssh:", util.validate_permission("root", "ssh"))
for acc in a.all_valid_accounts:
    print("资产账号:", acc.id, acc.name, acc.username)
PYEOF
```

判读：`get_permed_accounts_for_user()` 为空 → 该用户在本资产上**没有资产授权**，需在堡垒机补授权；返回值中账号的 `alias`（UUID）就是建令牌时要传的 `account`。

```bash
# 查看堡垒机侧的资产授权清单
docker exec -i -w /opt/jumpserver/apps jms_core python3 manage.py shell <<'PYEOF'
from perms.models import AssetPermission
for p in AssetPermission.objects.all():
    print(p.name, "| active=", p.is_active,
          "| users=", list(p.users.values_list("username", flat=True)),
          "| groups=", list(p.user_groups.values_list("name", flat=True)),
          "| accounts=", p.accounts, "| protocols=", p.protocols,
          "| nodes=", list(p.nodes.values_list("value", flat=True)))
PYEOF
```

## 八、验收记录（2026-10-14）

在 server 容器内以 `RuntimeApplicationService().execute(...)` 直接复现前端调用（等价于 `execute_capability` 的入参），`username=admin` / `ip=192.168.1.11`：

```json
{"success": true, "summary": "SSH terminal session created",
 "payload": {"terminal_url": "https://<堡垒机域名>/luna/koko/connect/?token=c26fb970-…&protocol=ssh",
             "asset_name": "192.168.1.11", "system_user": "root", "expire_seconds": 3600}}
```

- 资产匹配 → 用户解析 → 账号匹配 → 令牌创建（201）→ 终端 URL 生成，**全链路通过**；
- 生成的终端 URL 实测返回 `200`；
- 受测实例的资产授权为「账号 `@ALL` + 协议 `all` + 节点 `DEFAULT`」，覆盖全部资产与账号，故可直接连通；**换成按主机/账号细分的授权策略后，需确保平台自动创建的同名用户已入授权**。
