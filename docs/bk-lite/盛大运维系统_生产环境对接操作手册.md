## 1. 前置：网络连通性预检

一次 SSH 到 95 打包执行（通的标准是 TLS 握手成功，HTTP 码不限）：

```bash
# 95 → 钉钉开放平台（扫码登录、获取用户信息都走这两个域）
curl -sS -o /dev/null -w '%{http_code}\n' https://oapi.dingtalk.com/
curl -sS -o /dev/null -w '%{http_code}\n' https://login.dingtalk.com/

# 95 → 堡垒机（替换为实际地址；自签证书加 -k）
curl -ksS -o /dev/null -w '%{http_code}\n' https://<堡垒机地址>/
```

反向链路（无需登录 95，由用户侧验证）：

- 员工办公网浏览器可达 `https://10.10.2.95/`（443）；
- 钉钉回调是**浏览器侧跳转**（不是钉钉服务器回调 95），所以只要员工浏览器可达 95 即可；
- SSH 终端为**新标签页**打开堡垒机 Luna 页面，员工浏览器还需可达堡垒机地址。

任一不通 → 先找网络管理员开通策略，再进入后续步骤。

## 2. 钉钉企业登录对接

> 按钮级全流程见《盛大运维系统_钉钉登录对接操作手册》，本节只列 95 生产要点与顺序。

### 2.1 先定两件事（决策点）

| 决策 | 选项 | 建议 |
|---|---|---|
| 用哪个钉钉应用 | ① 复用 11 测试用的企业应用；② 为生产**单独创建**企业内部应用 | ②，凭证独立、测试互不影响（钉钉一个应用可配多个回调地址，复用也可行） |
| 未匹配处理策略 | 自动创建用户 / 拒绝登录 | 开放全员用「自动创建」；严格管控用「拒绝登录」——但 95 全新 DB 只有 admin 账号，选拒绝登录须**先批量导入/维护用户手机号** |

### 2.2 钉钉开发者后台（企业管理员操作）

1. 创建/选择企业内部应用，记录 **AppKey / AppSecret**；
2. **回调地址**添加（必须与实际访问地址完全一致）：

   ```
   https://10.10.2.95/api/v1/core/api/login_auth/callback/
   ```

3. **权限管理**开通：`Contact.User.Read`（必需）+ `Contact.User.mobile`（必需，敏感权限需企业管理员确认）；
4. 版本管理与发布，确认可见范围包含登录员工；
5. 交付 AppKey / AppSecret 给平台管理员（口头或加密渠道，不留文档）。

### 2.3 95 界面配置（平台管理员操作）

1. **系统管理 → 集成中心**：新增 DingTalk 实例（App Key / App Secret；Corp ID 留空）→ **测试连接**通过 → 保存，实例状态 ready；
2. **系统管理 → 登录认证**：新增认证 → 选钉钉实例 → 字段映射：平台字段 `phone` ↔ 外部字段 `mobile` → 选未匹配策略与默认用户组 → 保存并**启用**。

### 2.4 验证与注意

- **先在员工浏览器直接访问一次 `https://10.10.2.95/` 并信任自签证书**，否则扫码授权后回调跳转会被证书告警拦住（这是 IP + 自签环境最常见的"扫码后卡住"假故障）；
- 退出登录 → 登录页出现钉钉登录 → 扫码 → 手机号匹配已有账号或自动建号；
- 出现乱码用户名新账号 = 手机号权限未生效，回查 2.2 第 3 步；
- 后续上域名（见第 6 节）时**必须同步改回调地址**，否则登录立即失败。

## 3. JumpServer 堡垒机对接

> 原理与排错见《盛大运维系统_堡垒机对接文档》（尤其第〇章四件事、第七章排错）。

### 3.1 先定两件事（决策点）

| 决策 | 说明 |
|---|---|
| API Key 用哪个 | 建议为生产**单独新建**一个 Admin API Key（管理员级凭证，持有人登记台账）；测试用的可保留隔离 |
| `default_system_user` | 默认 `root`，须与堡垒机资产上实际存在的系统账号名核对；未命中直接失败（不回退） |

### 3.2 堡垒机侧（堡垒机管理员操作）

1. **系统设置 → API Key**：创建 Access Key / Secret Key；
2. **资产对齐**：堡垒机资产的 `address` 或 `name` 与 CMDB 主机 IP **精确相等**；
3. **授权核对**（对接失败的第一大原因）：目标用户（或其用户组）在该资产上的授权必须同时覆盖「**资产 × `ssh` 协议 × 系统账号**」三维；平台自动创建的同名堡垒机用户**默认无任何授权**，需管理员纳入授权后才能连。

### 3.3 95 界面配置（平台管理员操作）

**系统管理 → 集成中心**：新增 JumpServer 实例：

| 配置项 | 填写 |
|---|---|
| JumpServer 地址 | 堡垒机地址（**不含尾部斜杠**） |
| API Key / API Secret | 3.2 第 1 步获取 |
| 校验 SSL 证书 | 堡垒机自签证书 → **关闭** |
| 默认系统账号 | 与 3.1 决策一致（默认 root） |
| 自动创建用户 | 按需（默认开） |

测试连接通过 → 保存，实例状态 ready。

### 3.4 验收（必须用非超管账号）

1. CMDB 资产详情页 →「SSH 终端」按钮 → 新标签页打开 Luna 终端；
2. 令牌**5 分钟一次性**，超时重新点击；
3. 失败排错：`docker compose logs server` 按 `jumpserver_*` event 关键字定位（asset / user / token 哪一步失败），对照堡垒机文档 §7.2 排查顺序。

## 4. 告警通知渠道（内部触达）

平台支持渠道：**邮件 / 钉钉机器人 / 企业微信应用+机器人 / 飞书机器人 / 自定义 webhook / NATS**。生产建议先通钉钉群机器人（最快），邮件通道按公司 SMTP 实际情况补配。

操作（均在 95 界面）：

1. **系统管理 → 通知渠道**：新建渠道
   - 钉钉机器人：填群机器人 **webhook + 加签密钥**（钉钉群设置 → 机器人 → 添加自定义机器人时获取）；
   - 邮件：填公司 SMTP 的 host / 端口 / 账号 / 密码 / TLS 开关；
   - 保存后用渠道的**发送测试**验证收得到；
2. **告警中心 → 通知模板 / 通知策略**：绑定渠道，触发一条测试告警验证端到端。

## 6. 外部应用接入：集群管理（宫格直链型）

本章与第 2、3 章不同：钉钉与堡垒机走的是 **Provider 集成**（服务端有适配器与凭据存储）；「集群管理」走的是**零代码外部应用登记**——平台侧只在应用表里记一条 URL，**没有任何服务端调用与凭据传递**。以后再要接一个外部系统，照本节步骤做即可。

### 6.1 前置：确认对方服务本身可用

```bash
# 从办公网侧直接打对方入口（不走平台代理）
curl -s -o /dev/null -w '%{http_code}\n' http://10.10.2.95:18080/kubepi
# 期望 200。不是 200 就先去修对方服务，登记了也打不开
```

同时确认运行位置与边界：本模块独立 compose 项目 `kubepi`、目录 `/opt/kubepi`、卷 `kubepi-data`，与平台 `/opt/bk-lite` 互不隶属（详见 `docs/kubepi/架构与部署.md`）。

### 6.2 平台侧录入（界面操作，无代码）

系统管理 → 应用管理 → 新增：

| 字段 | 当前生产值 | 要点 |
|---|---|---|
| `name` | `kubepi` | **此值即授权挂钩**（`Role.app`）。建好后改名等于换一个授权项，旧授权全部落空 |
| `display_name` | 集群管理 | 宫格显示名，可随时改；对外只用模块名，不出现实现名 |
| `url` | `http://10.10.2.95:18080/kubepi` | 支持绝对地址，宫格是 `window.open` 直接打开 |
| `icon` | `ks1` | 可留空 |
| `tags` | `["集群管理"]` | 此处本应是翻译键体系；填自造字符串不报错但会原样显示 |

### 6.3 录入后必做的两步（不做就要么没人看得到，要么人人看得到）

**第一步 授权**：新建时会自动生成一个属于该应用的 `user` 角色（当前生产为 `system_mgmt_role` `id=49 · app=kubepi`）。到「应用管理 → 该应用 → 角色」把它授给该看到的角色。**不授权则任何人都看不到入口。**

**第二步 开通前必查一句**（真实存在过的越权可见风险）：宫格可见性过滤有一个短路条件——**用户只要拥有任一“不绑定应用”的角色，整个过滤会整段跳过**，该用户即可看到全部应用（包括刚登记的外部应用）。先只读查：

```sql
select id, name, app from system_mgmt_role where app = '' or app is null;
```

命中不等于配置错（超管类角色本应全域可见），但**必须逐个确认**它不该授给普通用户。

### 6.4 验收

- [ ] 用一个**已授权**账号登录，宫格能看到卡片，点开能到对方登录页
- [ ] 用一个**未授权**账号登录，宫格**看不到**该卡片（看得到即 6.3 第二步没做或短路条件未排除）
- [ ] 卡片打开是**新标签页且需单独登录**——这是外部应用的预期行为，不是单点登录故障

### 6.5 两个必须知道的坑

1. **改 `url` 是两步活。** 回表刷新的白名单只捞 `is_build_in=True` 的应用；手工登记的外部应用**不会刷新已有用户的应用快照**。改完地址必须同时重建相关用户的宫格卡片集合，否则用户仍跳旧地址。
2. **删 App 行不会剔除用户快照。** 界面删掉应用后，各用户控制台卡片里的残留入口仍在，点开会 404，需逐个处理用户应用快照。当前生产记录 `is_build_in=false`，**界面可直接删**（只有被标内置的才拒删）。字段当前值与兜底 SQL 见 `docs/kubepi/版本与变更台账.md` T3。
