> 类型：设计文档（spec）· 规划产物，非长期手册

> 范围：为「集群管理」模块补齐与 bk-lite 对称的规范化资产

## 1. 摘要

KubePi 已作为外部服务引入，并在平台「应用管理」中登记为「集群管理」模块，生产在用。但 bk-lite 周围长期形成的规范化资产体系（源码仓锚点、部署资产、使用文档、架构文档、对接手册、部署/运维手册、版本与变更台账、AI 交接文档）**在「集群管理」这一侧一份都没有**，现状是靠一份 2026-11-05 的方案文档和服务器上的一堆文件在撑。

本方案不推进任何新功能，只做一件事：**对照 bk-lite 已有的每一份资产，为「集群管理」建出对称的那一份**，并顺手订正三处会导致误操作的文档失真。

## 2. 已定决策（本方案内不再留待定）

| # | 决策点 | 结论 | 理由 |
|---|---|---|---|
| D1 | 补课组织方式 | **方式一 · 事实归位到既有手册**，`集成方案` 降级为决策存档 | 真相必须放在最常被打开的地方；否则手册里的硬数字（18 个 running）会持续说谎 |
| D2 | 资产归属 | **按服务分目录**（微服务式模块化）：可执行资产 `ops/<service>/`，技术文档 `docs/<service>/`。平台现有 4 个脚本一并从 `ops/` 迁入 `ops/bk-lite/`，`ops/` 不再直接放文件 | 一个服务的资产一个目录；混放会导致接手人无法判断某脚本属于谁 |
| D3 | 模块命名 | 对外一律 **「集群管理」**（与库内 `display_name` 一致），`KubePi` 仅作为实现名出现在版本台账与附录 | 直接沿用现有命名铁律，无需为它开例外 |
| D4 | `app.yml` 处理 | **接受镜像默认（不挂载、不进仓、不进备份）** + 钉一条带触发条件的红线（见 5.3） | 当前没有任何主动设置的值，选挂载是为一个还没用到的能力提前背上与上游漂移的债 |
| D5 | 本轮交付顺序 | 清单 → spec → 实施计划 → 分批落地 | 服务器侧全部为只读，不落变更 |
| D6 | spec / plan 存放 | `bk-lite/docs/specs/` 与 `bk-lite/docs/plans/`（非技能默认的 `docs/superpowers/*`） | 有版本管理，又与长期手册明确区分 |
| D7 | 分层命名规则 | **目录与服务名用实现名**（`ops/kubepi/`、`docs/kubepi/`）——运维对象就是服务；**面向使用者与产品级手册用模块名**（「集群管理」）——使用者对象是平台宫格，不是后端服务 | 使 D3 的命名铁律与目录规范不打架；使用者无需知道 KubePi 存在 |
| D8 | 使用文档不拆目录 | `17_集群管理.md` **仍留在 `盛大运维系统_使用文档/` 单一册系内**，不进 `docs/kubepi/` | 把用户手册按后端服务拆开，恰恰会造成使用者混淆，与本决策目标相反 |

### 3.1 `docker-compose.yml` 权威内容（已从 95 取回，逐字入仓）

```yaml
services:
  kubepi:
    image: 1panel/kubepi:v2.0.3
    container_name: kubepi
    restart: unless-stopped
    ports:
      - "18080:80"
    volumes:
      - kubepi-data:/var/lib/kubepi
networks:
  default:
    name: kubepi
volumes:
  kubepi-data:
    name: kubepi-data
    external: true
```

入仓判据：与 `95:/opt/kubepi/docker-compose.yml` `diff` 为空。注意备份目录里已含 `docker-compose.yml.snapshot`，但**备份与生产同机同盘，不能替代仓库**。

### 3.2 `backup-kubepi.sh` 移位的连带动作

脚本本体不改。移动后必须在**同一批**里改掉两处引用，否则造出"仓库挪了、手册还指旧路径"：
1. 集成方案 8.4 与附录 E 中的 `bk-lite/ops/backup-kubepi.sh` 路径；
2. 运维手册 §七 脚本与文件清单。

线上 `/opt/kubepi/backup-kubepi.sh` 为独立副本，本轮**不动线上**。

### 3.3 `cron.d-kubepi-backup` 入仓内容

```
# KubePi 数据每日备份（独立于平台备份任务，02:40 跑在平台 02:30 之后）
# 脚本内部已 tee 到 /var/log/kubepi_backup.log，故此处不再重定向到同一文件（避免行重复）
40 2 * * * root /opt/kubepi/backup-kubepi.sh > /dev/null 2>&1
```
文件头注释写明安装方式（`install -m 644 cron.d-kubepi-backup /etc/cron.d/kubepi-backup`）。

### 3.4 `.tmp-kubepi/` 40 个临时文件的三分类取舍

| 处置 | 文件 | 判据 |

### 4.1 T3 必须写清的两条操作事实

1. **改 `url` 是两步活**：`is_build_in=f` → `current_user_apps` 的回表刷新白名单只捞 `is_build_in=True`（源码 `console_mgmt/viewsets/user_app_set.py:100`），因此改 App 表后**已有用户的应用快照不会刷新**，需同步重建用户应用快照。
2. **界面上可删除**：`AppViewSet.destroy` 只对 `is_build_in=True` 拒删，本行是 `f` → **可删**，无需先改标记。集成方案附录 F 的相反表述在 6.2 节订正。

### 4.2 面板内容清单（M2，需单独授权）

T5「面板资产清单」（导入了哪些集群、面板侧有哪些账号）需要读 bbolt，只能通过备份快照在**隔离容器**里只读导出。bbolt 有独占锁，严禁在生产实例运行时打开同一份库。该动作涉及 `create` 临时容器，**须单独确认**，不在本轮默认范围。

### 5.3 三处会导致误操作的失真（必改）

| # | 失真 | 影响 | 修法 |
|---|---|---|---|
| **F1** | 集成方案 §6.1 用「`is_build_in=True` 时改 App 表即全量生效」论证拆除反代；实测本行为 `f` | 运维照此理解会以为改一处 url 就够，实际改了不生效 | 该条论证作废并改写；反代决策本身**不重评**（第二、三条理由与成本核算仍成立） |
| **F2** | 手册多处「服务总数应为 18 个 running」判据，实际 19 | 巡检误判为异常 | 全文改为「平台 18 + 外挂 1 = 19」，并逐处 grep 校验 |
| **F3** | `app.yml` 不在卷内也不在备份内（D4 决定接受） | 重建容器 → jwt key 重生成 → 全员会话失效，会被当故障排查 | 运维手册故障速查与部署手册升级节各写一条「重建后需重新登录，属预期」；并钉红线：**一旦需修改 app.yml 任何值（TLS / session.expires / db.path），同一次变更内必须一并挂载持久化 + 进仓 + 纳入备份，否则该修改会在下次容器重建时静默失效** |

`F3` 的红线与坑册 15/18（`install.run` 静默重写 `.env`）属同一族：**改了但不落持久层 = 下次重建静默丢失**，交叉引用。
