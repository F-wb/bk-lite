# 集群管理模块 · 架构与部署

> 模块对外名称：**集群管理**（平台应用宫格显示名）。实现为第三方 Kubernetes 图形面板，目录与服务名用实现名 `kubepi`。
> 本文件是**架构与部署说明**；事实参数（镜像版本、digest、已纳管集群、账号、变更史）唯一权威是 `版本与变更台账.md`；
> 设计取舍与否决理由在 `../bk-lite/盛大运维系统_集群管控集成方案.md`。三者不重复记录同一个值。
>
> **本模块不含跨服务的认证打通与权限模型设计**——两套账号体系各自独立是**当前既定现状**，不是本文件的待办。

## 1. 模块定位与职责边界

| 维度 | 内容 |
|---|---|
| 解决什么问题 | 平台缺少图形化的 Kubernetes 集群操作入口：看负载、看 Pod 日志、进容器排障、临时重启/扩缩 |
| 在平台中的形态 | **外挂模块**：平台侧只有一条应用表记录（宫格直链），**无后端代码、无路由、无数据表迁移、不进 `INSTALL_APPS`** |
| 唯一的平台侧变更 | `system_mgmt_app` 一条外部应用记录（字段与回滚 SQL 见台账 T3） |
| 不负责什么 | 发布与回滚（走流水线打 tag）、集群生命周期（建集群/升级/证书轮换）、台账与指标与告警（留在平台）、无人值守自愈 |
| 使用者 | 运维组（日常）；研发组接入属未决项，前置条件见 §7 |

**一个动作只有一个入口**：改镜像版本 / 编辑 YAML / 生产写操作 = 流水线；观察与应急 = 本模块；台账指标告警 = 平台。这条是边界的核心，不是建议。

## 2. 组件与数据流

```
浏览器
  ├──▶ 平台（traefik :443）──▶ server / web          ← 平台自身链路
  └──▶ 宫格卡片「集群管理」window.open ──┐
                                        ▼
                              面板 kubepi（:18080 → 容器内 80）
                                        │ 作为普通 RBAC 客户端
                                        ├──▶ 121 apiserver
                                        └──▶ 110 apiserver
```

三条链路的性质差别很大，必须分清：

| 链路 | 内容 | 是否调用服务端 | 是否传凭据 |
|---|---|---|---|
| 平台 → 面板 | 仅浏览器侧 `window.open` 打开一个 URL | **否** | **否** |
| 面板 → 集群 | 面板按自己库里的集群配置连接 apiserver | 面板自己的事 | 凭据只存面板库 |
| 平台 → 集群 | **不存在这条链路** | — | 平台**不持有 kubeconfig、不直连 apiserver** |

平台侧因此**没有任何运行时依赖**指向面板：面板整体停机时，平台功能零异常（故障隔离见 §6）。

## 3. 部署形态与选型结论

选定 **与平台生产机（`10.10.2.95`）同机混部**，独立 compose 项目。理由与被否决的备选（91 构建机承载 / 121 集群内 Deployment / 独立虚机 / 前置反代容器）的完整对比与实测依据，见集成方案 §6、§6.1、§8.1；本文件不复制那份论证。

一句话结论：复用主机且实测无资源竞争，代价是备份边界与攻击面需自行闭环——两者都已在台账与待办中登记，不是未知项。

## 4. 目录与卷

| 层 | 路径 | 说明 |
|---|---|---|
| 线上编排与脚本 | `/opt/kubepi/`（`docker-compose.yml`、`backup-kubepi.sh`） | 与 `/opt/bk-lite` 完全隔离；平台安装器与 `apply-state.sh` **碰不到** |
| 线上数据 | 命名卷 `kubepi-data` → 容器内 `/var/lib/kubepi` | **必须保持 `external: true`**（防 `down -v` 误删生产库） |
| 线上运行配置 | 容器内 `/etc/kubepi/app.yml` | ⚠️ **不在卷内、不在快照内**（在容器可写层）；见 §8 红线 |
| 仓库可执行资产 | `ops/kubepi/`（compose、cron、backup、restore、export、README、panel-assets） | 同步方向以**仓库为准**；compose 与线上逐字节相等（已实测） |
| 本模块技术文档 | `docs/kubepi/`（本文件 + 版本与变更台账 + panel 清单相关说明） | 按服务分目录；与可执行资产 `ops/kubepi/` 同一服务名 |
| 产品级手册 | `docs/bk-lite/`（盛大运维系统_*.md 与 使用文档/） | 2026-11-09 由仓库根迁入本目录（仓库根现只留 `AI_HANDOVER.md`）；**使用文档不拆进 `docs/kubepi/`**，因为使用者面对的是单一平台宫格 |

## 5. 端口与访问路径

| 项 | 值 | 备注 |
|---|---|---|
| 宿主端口映射 | `18080:80`（实测监听 `0.0.0.0`，含 IPv6） | 无 TLS |
| 入口 | `http://10.10.2.95:18080/kubepi` → `200` | **明文 HTTP**，已知情接受；重新评估条件见 §7 |
| 来源限制 | 宿主机 `iptables` 对该端口**无任何规则**（实测） | "只开放办公网"目前**仅靠上游网络策略**，本机无护栏 |
| 平台侧入口 | 应用宫格卡片「集群管理」 | 新标签页打开；**需单独登录**（非单点登录） |

## 6. 依赖与故障隔离（实测依据，非设计愿望）

| 断言 | 实测证据 |
|---|---|
| 面板挂不影响平台 | 面板重启期间平台侧无接口依赖，无连带异常；隔离前提是 §2 表里"不存在平台→apiserver 链路" |
| 平台重建/升级不影响面板 | 安装器 `install.run` / `bootstrap.sh` / `ops/bk-lite/apply-state.sh` 作用域均不含 `/opt/kubepi` |
| 资源无竞争 | 面板常驻约 55 MiB（2026-11-05 记录），非 privileged，`restarts=0` |
| 可摘除 | 删应用记录 + 清理用户应用快照 + `docker compose -p kubepi down`，平台无残留 |

**两个口径**（极易被误判为异常）：`docker compose ps -q | wc -l` = **18**（平台）；`docker ps -q | wc -l` = **19**（整机，含本模块）。

## 8. 备份边界与一条红线

**平台备份任务不覆盖本模块，本模块备份任务也不覆盖平台。** 两个独立 cron（`02:30` 平台、`02:40` 面板，均为 **UTC**）。

- 面板库是 **bbolt 单文件 + 独占文件锁** → 备份必须**冷拷贝**（短暂停容器约 2 秒），不能在线 `cp`。
- **绝不允许两个实例同时打开同一份数据**；验证可还原性走 `ops/kubepi/restore-kubepi.sh --verify-only`（临时卷，不碰生产）。
- 还原步骤的**唯一权威**是 `ops/kubepi/restore-kubepi.sh`，本文件与其他文档只引用不复制。
- 备份结果的健康度由 `ops/bk-lite/backup-watchdog.sh` 判定——它检查"产物能否用于还原"，不检查退出码。

> **红线**：`/etc/kubepi/app.yml` 位于容器可写层，其中 `jwt.key` 由首次启动随机生成。因此**升级或重建容器后所有面板会话失效、需重新登录，属预期行为**。但一旦需要修改 `app.yml` 里任何值（`ssl.enable`/`certificate`、`session.expires`、`db.path`），**同一次变更内必须一并把它挂载出来持久化 + 入仓 + 纳入备份**，否则该修改会在下次容器重建时被镜像默认值静默覆盖。
